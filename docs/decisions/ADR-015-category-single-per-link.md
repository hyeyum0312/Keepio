# ADR-015: 링크당 카테고리는 하나로, 삭제는 영구·병합은 별칭으로

- Status: accepted (2026-11-14)
- Context / problem:
  - PRD v0.3과 `standards/PRODUCT.md`는 링크↔카테고리 N:M(한 링크에 여러 카테고리)을 확정으로 적었다. 카테고리 기능은 아직 구현 전이다.
  - 사용자 검토(2026-11-14): 카테고리의 목적은 "링크를 쉽게 찾기"인데 여러 카테고리에 들어가면 어디에 뒀는지 헷갈리고 관리하기 어렵다. 저장할 때 카테고리를 고를 수도, 안 고를 수도 있어야 하고, A에 넣은 링크를 나중에 B로 옮길 수 있어야 한다.
  - 카테고리 삭제·병합 방식은 데이터를 되돌리기 어려워 함께 결정한다.
  - 기획서: [CAT-01 카테고리·태그 정책 기획서](https://claude.ai/artifact/TiYqnwWyza9FGxkXQw4jh8)
- Options:
  - 구조
    - (a) N:M 유지 + 화면에서 "이동/추가" 둘 다 제공: 데이터는 유연하지만 사용자가 매번 이동과 추가를 골라야 하고, 같은 링크가 여러 곳에 보인다.
    - (b) 링크당 0~1개(1:N): 링크는 늘 한 곳에 있다. 여러 기준으로 묶는 일은 태그(자유, 여러 개)와 버킷(중복 허용)이 맡는다.
  - 삭제: (a) 휴지통 / (b) 영구 삭제 + 확인 창
  - 병합: (a) 2차로 미룸 / (b) 1차 포함, 옛 이름을 별칭으로 남김
- Decision:
  - 구조 (b). 카테고리는 링크당 0~1개, 없으면 미분류(D-02). 저장 시 선택은 선택 사항. 이동은 연결만 바꾸고 원본·태그·버킷 연결은 그대로 둔다.
  - 태그는 링크에 단다(카테고리 안에 두지 않는다). 카테고리 화면은 그 카테고리 링크에 쓰인 태그만 필터로 보여 준다.
  - 버킷은 기존대로 여러 버킷에 중복 가능, 한 버킷 안에서는 한 번.
  - 삭제 (b). 카테고리를 지우면 그 안의 링크는 남고 미분류가 된다. 확인 창에 영향받는 링크 수를 보여 준다.
  - 병합 (b). A를 B로 합치면 A의 링크가 모두 B로 옮겨지고 A 이름은 B의 별칭이 된다. 별칭은 병합으로만 생긴다(이름 변경 시 옛 이름은 버린다).
- Consequences / side effects:
  - `bookmark_categories` 연결 테이블 대신 `bookmarks.category_id`(NULL 허용)를 쓴다. 조회·필터가 단순해진다.
  - AI 분류는 카테고리 1개 + 태그 여러 개를 제안한다(PRD AI 정책 4번 변경).
  - 한 링크를 두 카테고리에서 동시에 보고 싶은 경우는 태그나 버킷으로 해결해야 한다. 베타에서 불편이 확인되면 재검토한다.
  - 카테고리 휴지통이 없으므로 실수로 지운 분류는 복구할 수 없다(링크는 안전).
  - 소유 주체(사용자 vs 워크스페이스)는 이 ADR 범위가 아니다. 지금은 `user_id` 소유로 둔다(OPEN-QUESTIONS D-15).
- Verification: FEAT-008 AC-03·04·05·09를 실제 PostgreSQL 통합 테스트로 확인한다.
- Rollback / migration: 다시 N:M이 필요하면 `bookmarks.category_id` 값을 새 연결 테이블로 옮기는 마이그레이션 1회와 API `categoryId` → `categoryIds` 변경이 필요하다. 앱(2차) 출시 전에 결정해야 API 버전 관리 없이 바꿀 수 있다.
